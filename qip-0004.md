## Abstract

This document describes the integration of post-quantum cryptography (PQC) into the litep2p networking stack used by the Quantus Network.
The implementation uses Dilithium (ML-DSA) for peer identity and ML-KEM-768 for Noise key encapsulation, providing quantum-resistant authentication and transport security.

## Motivation

Classical libp2p stacks rely on algorithms vulnerable to Shor's algorithm. As quantum computers advance, quantum-resistant networking becomes critical for long-term security. Quantus ships PQC networking in-tree via litep2p (the sole supported network backend); earlier standalone `qp-libp2p-*` forks are archived and unused by the chain.

## Specification

### Peer identity (ML-DSA-87)

- Node identity keys are Dilithium only: `NodeKeyConfig` / CLI `NodeKeyType` each have a single variant, `Dilithium`
- Networking identity is **ML-DSA-87 only** (`client/litep2p/src/crypto/dilithium.rs`). The separate CLI `CryptoScheme` enum (ML-DSA-87 / ML-DSA-65) applies to keystore/account commands, not node keys
- There is no Ed25519 / classical node-key option
- Key material may be freshly generated, loaded from a file, or supplied as raw bytes (`Secret::{New, File, Input}`)

### Transport security (ML-KEM-768 Noise)

Noise uses Clatter with the **pqXX** handshake pattern and ML-KEM-768 (FIPS 203). The session type is hardcoded to a post-quantum handshake (`PqHandshake<MlKem768, MlKem768, ChaChaPoly, Sha256>`); there is no X25519 fallback path. The pattern transmits KEM public keys (`e`, `s`) and performs KEM encapsulations (`ekem`, `skem`); there are no Diffie–Hellman tokens (`ee` / `es` / `se` / `ss`).

**Handshake flow (Clatter `noise_pqxx()` — 4 messages):**

```text
-> e
<- ekem, s
-> skem, s
<- skem
```

(Identity payloads may accompany the messages that carry static keys, per the litep2p Noise framing.)

### Substrate network layer

- `chain/client/network` supports **only** the litep2p backend (libp2p backend modules have been removed)
- PQC crypto lives in `chain/client/litep2p/src/crypto/` (`dilithium.rs`, `noise/`)
- Default node key generation is Dilithium

## Implementation Details

### Dependency Management

Networking Dilithium support depends on the published crate (example from the chain workspace):

```toml
qp-rusty-crystals-dilithium = { version = "4.0.0" }
```

(Earlier archived identity crates used an optional crates.io dependency such as `qp-rusty-crystals-dilithium = { version = "2.1.0", optional = true }`.)

### Key Size Considerations

| Algorithm | Public Key Size | Private Key Size | Signature / CT Size |
|-----------|----------------|------------------|---------------------|
| ML-DSA-87 | 2592 bytes     | 4896 bytes       | 4627 bytes          |
| ML-KEM768 | 1184 bytes     | 2400 bytes       | 1088 bytes          |

### Security Parameters

**Dilithium (ML-DSA-87):**
- NIST Category 5 (FIPS 204)
- Based on Module Learning With Errors (M-LWE)

**ML-KEM768:**
- NIST Category 3 (FIPS 203)
- Based on Module Learning With Errors (M-LWE)

## Performance Considerations

**Computational Overhead:**
- Dilithium signatures: [~7-10x slower signing than Ed25519](https://blog.cloudflare.com/pq-2024/) and [similar verification times to Ed25519](https://s.itho.me/ccms_slides/2024/5/23/4414254e-124d-4bbd-8a41-579706b59401.pdf)
- ML-KEM operations: [similar encapsulation and decapsulation times](https://blog.cloudflare.com/pq-2024/) with larger key/ciphertext sizes

**Network Overhead:**
- Increased handshake message sizes due to larger public keys
- Higher CPU for signature verification
- Four-message pqXX handshake (vs classical Noise XX's three messages; classical XX is DH-based and has no KEM rounds)

## Rationale

**Algorithm Selection:**
- **ML-DSA-87**: NIST standardization, conservative security parameters, reasonable performance
- **ML-KEM-768**: Balance between security level and performance for key exchange

The security of p2p connections in a blockchain is important, but failure of their cryptography is not catastrophic.
Specifically, if a node's libp2p/litep2p keys were compromised, the attacker could impersonate nodes or decrypt communication between nodes.

Nodes are already assumed to be possibly malicious and are therefore generally untrusted in the blockchain security model.
Invalid transactions will not be included regardless of who sent them. Transactions are signed by users, not nodes, and
nodes will eventually drop peers that misbehave. A large scale attacker could potentially knock many nodes off the network
by impersonating them and sending invalid messages, which is why we choose the highest security setting for identity.

Decrypting p2p communication does not confer tremendous benefits to the attacker, as the messages passed among
the nodes generally make it on chain eventually and are therefore expected to be public. The primary benefit to the attacker
would be that they could track a given transaction's path thru the network, potentially narrowing down the geography or
IP address of the owner of a particular key. This attack is unlikely to be carried out by anyone other than a state actor
and is defeated by users connecting to the network thru proxies, VPNs or Tor. Therefore, we choose the medium security level (768)
for ML-KEM.
