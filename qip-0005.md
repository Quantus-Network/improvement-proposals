## Abstract

This document describes an aggregated post-quantum signature scheme for blockchains using zero-knowledge proofs. It moves balance-verification off-chain so that on-chain verification simply has to verify a single proof and update balances. It uses provably-unspendable addresses and nullifiers to prevent double-spends and storage-proofs to prove that funding took place. These signatures can be aggregated because the proof system we use ["plonky2"](qip-0005/QIP-0005-2.pdf) supports aggregation via recursion. Aggregation is implemented as a multi-layer tree, with a privacy-sensitive layer-0 and a layer-1 intended for third-party aggregators.
The limiting factor becomes the aggregated public inputs. In the current scheme, each leaf transfer contributes (in the final aggregated proof) one nullifier plus up to **two** output slots (exit accounts + amounts), while higher layers forward these slots and nullifiers and add a small fixed overhead.   
We call this scheme "entangled addresses" because the unspendable addresses and exit addresses are invisibly linked, like entangled qubits.

## Motivation

Transitioning to a post-quantum era in blockchains introduces a scaling challenge because post-quantum signatures and public keys are many times larger than those of elliptic curves and these typically need to be revealed to make a transaction. Secure hash algorithms (Poseidon in our case) are generally weakened but not destroyed by quantum algorithms (specifically Grover's). In fact, some post-quantum signature schemes such as SPHINCS+ are built on top of the security of secure hash functions, so proving knowledge of a preimage can suffice as a post-quantum signature scheme.

### ZK Circuit Details

**Public Inputs:**

- `asset_id`: The identifier for the asset being transferred (0 for native token).
- `output_amount_1`: Primary output amount, exposed as a `u32` quantized with 0.01 units of precision. On-chain, the amount is stored as a `u128` with 12 decimal places; during on-chain verification, we reconstruct this `u128` by multiplying `output_amount_1` by 10^10 (so that 10^2 × 10^10 = 10^12 total decimal precision).
- `output_amount_2`: Optional secondary output amount (change or split payment), also a `u32` quantized with 0.01 precision. Set to 0 if unused.
- `volume_fee_bps`: Volume fee rate in basis points (1 basis point = 0.01%). This is verified on-chain to match the runtime configuration.
- `nullifier`: A unique, transaction-specific value derived from private information. Its purpose is to prevent double-spending by ensuring that a given set of private inputs can only be used to generate one valid proof.
- `exit_account_1`: The public address where `output_amount_1` is intended to be sent after the proof is verified.
- `exit_account_2`: The public address where `output_amount_2` is intended to be sent (all zeros if unused).
- `block_hash`: A commitment (Poseidon2 hash) to the block header fields used inside the circuit.
- `block_number`: The block height corresponding to `block_hash`. This is public so the verifier/aggregator can check that it matches the associated header.

**Private Inputs:**

- `secret`: A confidential, randomly generated value unique to the prover, serves as a primary secret for deriving other transaction components.
- `storage_proof`: A storage proof of a Merkle Patricia trie proving inclusion of the relevant wormhole storage leaf (e.g., `TransferProof`) in the state under the provided `state_root`.
- `transfer_count`: A per-recipient-account unique ID for the transfer (monotonically increasing), ensuring nullifiers are unique.
- `funding_account`: The account ID associated with the source of the funds (the sender). Used to derive the nullifier and confirm ownership.
- `unspendable_account`: An account ID derived from the `secret` that, when hashed, produces a verifiable "burn" (unspendable) address.
- `state_root`: The state root of the Substrate block (the Merkle-Patricia trie root for the state).
- `extrinsics_root`: The extrinsics root of the block header.
- `digest`: The raw header digest field (110 bytes), encoded injectively into a fixed number of field elements for use inside the circuit.
- `parent_hash`: The parent hash of the block header. **This is private** and is only used inside the circuit to compute `block_hash` from the header preimage (binding the header fields to the public commitment).
- `input_amount`: The input amount from storage (before fee deduction), quantized with 0.01 units of precision. The circuit verifies that:
  - `(output_amount_1 + output_amount_2) * 10000 <= input_amount * (10000 - volume_fee_bps)`.


> Note: Instead of passing a monolithic `block_header` preimage into the circuit, we pass the structured header fields (`parent_hash`, `block_number`, `state_root`, `extrinsics_root`, `digest`) and recompute a Poseidon2 hash from them inside the circuit. That hash is constrained to equal the public `block_hash`.

### Miner Address Enforcement

The chain enforces that all miners use entangled addresses for their block rewards. When a miner submits a block, they must provide a 32-byte preimage of their reward address. The chain hashes this preimage and sends rewards to the resulting address. Since dilithium public keys are much larger than 32 bytes, a valid 32-byte preimage cannot be a public key, ensuring the reward address is an entangled (unspendable) address. This mechanism guarantees that all mining rewards flow through the wormhole system, maintaining the integrity of the entangled address scheme across the network.

### Client / Prover Flow

User generates what appears to be a normal account but is provably unspendable "Proof-of-Burn". The account is unspendable because, instead of being a single-hash of a public key like a normal account, it is the double-hash of a salt + secret. The salt + double hashing protects the system from false-positives, where the zk-proof is convinced that the account is unspendable but actually the digest is a single-hash of a public key and therefore spendable. The security of the construction therefore reduces to finding the preimage of a preimage of a digest.

Users retain this proof of unspendability (secret pre-image) for later claims. Any tokens that are sent to the address are therefore provably burned, and so they can be re-minted without changing the total token supply. Each transfer of tokens to the address generates a [TransferProof](https://github.com/Quantus-Network/chain/blob/main/pallets/wormhole/src/lib.rs#L173) storage object. The user's wallet can generate a storage proof for each transfer. This storage proof is a merkle-patricia-trie (MPT) proof from a recent storage root (stored in block header) down to a specific storage item (`TransferProof` in this case). The MPT proof is similar to a Merkle proof, except that instead of each parent being the hash of the children, the hash of each child is part of the parent's data.

The TransferProof contains various data about the transfer, including the per-recipient count of such TransferProofs, which makes each TransferProof unique. This count is included in the nullifier preimage along with a salt and the users secret.

The secret used to create both the nullifier and the unspendable-account must be retained by the wallet and should therefore be derived deterministically from the wallet seed, similar to private/public keys.

Because Substrate doesn't natively cache storage roots (only block hashes up to a certain depth), and the verifier needs a way to check that the storage root is valid, we include the `block_hash` and `block_number` of the block header that contains the storage root as public inputs to the circuit. The circuit binds the storage root to the public commitment by recomputing `block_hash` from structured header fields inside the circuit.

### Aggregator Flow

Anyone can aggregate proofs and submit the resulting aggregated-proof to the chain. However, aggregation is structured as a multi-layer tree, and the **privacy properties differ by layer**, so we recommend different operational roles at each layer.

#### Recommendation: Layer-0 should be client-local

Although layer-0 aggregation is permissionless, **we recommend that layer-0 is used exclusively to aggregate a client’s own set of wormhole proofs** (i.e., performed locally by the wallet/client).

Layer-0 is the layer where leaf proofs are padded with dummy proofs and where proof ordering / slot behavior is used to hide which transfers are real. If a client delegates layer-0 aggregation to a third party, that third party will typically learn (or be able to infer) **which leaf slots are real vs dummy** for that client’s batch (e.g., from the raw set of proofs provided, the count of real proofs, or the aggregation inputs prior to shuffling/padding). Revealing dummy locations materially weakens privacy because it makes **balance-linking analysis** much easier for the aggregator: the aggregator can narrow which output slots correspond to real transfers and correlate amounts/exit slots across time.

For this reason, layer-0 is treated as a **privacy-sensitive step** and should be executed by the client/wallet whenever possible.

#### Recommendation: Layer-1 is intended for delegated aggregation

Layer-1 aggregation, by contrast, operates over **already-aggregated layer-0 proofs** and simply verifies invariants and forwards the fixed-layout public inputs. At this stage, the delegated aggregator does not receive (and does not need) per-leaf “raw” proof sets or padding decisions; it aggregates **opaque layer-0 aggregates** whose internal dummy positions are already hidden inside a verified proof.

As a result, layer-1 does **not introduce the same privacy risks** as delegating layer-0, and is therefore the intended layer for **third-party / delegated aggregation** (e.g., run by miners, professional aggregators, or other infrastructure operators) to reduce on-chain submission overhead and collect aggregation fees.

#### Layer-0: aggregate leaf transfer proofs (client-local)

Layer-0 takes `N` leaf proofs (wormhole transfer proofs) and produces a single layer-0 aggregated proof. This step is privacy-sensitive due to dummy padding and should generally be performed by the client.

#### Layer-1: aggregate layer-0 aggregated proofs (delegated)

Layer-1 is intended for third-party aggregators who collect multiple layer-0 batches (from many clients) and combine them into a single proof for on-chain submission. Because it aggregates verified layer-0 proofs as opaque objects, it does not expose client dummy placement and is suitable for delegated operation.

#### Aggregated public input layouts

**Layer-0 aggregated proof output layout**

Layer-0 outputs a fixed-layout public input vector:

```text
[
  num_exit_slots(1),              // fixed = 2*N (two outputs per leaf)
  asset_id(1),
  volume_fee_bps(1),
  block_hash(4),
  block_number(1),
  [sum(1), exit_account(4)] * (2*N),
  nullifier(4) * N,
  padding...
]
```

> Note: Exit slots are always 2*N (Bitcoin-style 2-output layout). Slots that are duplicates (within the batch) are zeroed (sum = 0 and exit_account = 0).Dummy leaves are detected via block_hash == 0. Dummy leaf nullifiers are overridden with random dummy nullifiers in the wrapper output to prevent on-chain collisions.

**Layer-1 aggregated proof output layout**

Layer-1 aggregates M layer-0 proofs (each itself representing N leaves) and outputs:

```text
[
  aggregator_address(4),          // identifies the layer-1 operator for fee collection
  asset_id(1),
  volume_fee_bps(1),
  block_hash(4),
  block_number(1),
  total_exit_slots(1),            // = M * (2*N)
  [sum(1), exit_account(4)] * total_exit_slots,
  nullifier(4) * total_nullifiers,// = M * N
  padding...
]
```
> Note: Layer-1 forwards exit slots and nullifiers from each child layer-0 proof in order. Dummies at the layer-0 level propagate as block_hash == 0 in the layer-0 header and are permitted by layer-1’s “matches ref OR dummy” block constraint.

The deduplication and summing reduce the storage requirements for the chain. This aggregation process can be recursed, so that the many proofs being aggregated become leaves in a tree.

It's important to note that **all leaf proofs in an aggregated batch must use the same proof-generation block**. The aggregation circuit enforces that all real proofs (those with `block_hash != 0`) reference identical `block_hash` values. However, cross-block batching is still possible because `TransferProof` entries persist indefinitely in the state trie: a transfer recorded in block X remains accessible at block Y (for any Y > X). To batch transfers from multiple blocks, a prover can generate storage proofs for all desired transfers against a single later block's `state_root`, and aggregate those proofs with a shared `block_hash`.

### Chain / Verifier Flow

The chain / verifier receives a proof that may be:
- a layer-0 aggregated proof, or
- a layer-1 (or higher) aggregated proof intended for on-chain submission.

The chain must check:

- The `block_hash` and `block_number` correspond to a valid block in the chain (per runtime constraints / depth window).
- The `volume_fee_bps` matches the current runtime configuration.
- The supplied proof is valid for the expected verifier circuit (layer-0 / layer-1).
- Each included `nullifier` has never been used before.
- For each non-zero exit slot (`exit_account != 0`), mint/transfer the corresponding `sum` to that account (after reconstructing `u128` from quantization), and apply fees per runtime rules.
- If present (layer-1+), `aggregator_address` is used to attribute and/or distribute aggregator fees (policy defined by the runtime).

### Circuit Logic

The zk-circuit verifies the following:

1. **Dummy Proof Detection**
   - If `block_hash == 0` and both `output_amount_1 == 0` and `output_amount_2 == 0`, the circuit treats the proof as a dummy and skips the storage proof, header, and nullifier checks. This enables universal dummy proofs for aggregation padding.

2. **Nullifier Derivation**
   - Computes `H(H(salt || secret || transfer_count))` where salt is the 8-byte string "~nullif~"
   - Compares the derived value against the provided `nullifier` public input

3. **Unspendable Account Derivation**
   - Computes `H(H(salt || secret))` where salt is the 8-byte string "wormhole"
   - Compares the derived value with the provided `unspendable_account`

4. **Storage Proof Verification**
   - The circuit verifies the `storage_proof` to confirm that a specific leaf (the transfer record) is part of the Merkle Patricia trie with root `state_root`
   - To verify that the storage proof is valid, the circuit traverses the tree in root-to-leaf order, and for each node:
     1. Compares the expected hash against the hash of the current node (verifies inclusion)
     2. Updates the expected hash to be equal to the hash of the current node
     3. If this node is the leaf node: additionally verifies that it includes the hash of the leaf inputs (transfer record)

5. **Block Header Commitment Verification**
   - Inputs: `block_number` (public), `parent_hash` (private), `state_root` (private), `extrinsics_root` (private), `digest` (private, 110 bytes mapped injectively to field elements)
   - Steps:
     1. **Range-check `block_number`**: The circuit constrains `block_number` to be a 32-bit value to ensure it matches the canonical encoding used outside the circuit
     2. **Build header preimage**: `preimage = parent_hash || block_number || state_root || extrinsics_root || digest`
     3. **Poseidon2 hash**: `computed_hash = Poseidon2Hash(preimage)` using `hash_n_to_hash_no_pad_p2::<Poseidon2Hash>`
     4. **Connect to public `block_hash`**: The circuit enforces `block_hash == computed_hash`

6. **Fee Calculation Verification**
   - The circuit verifies:
     - `(output_amount_1 + output_amount_2) * 10000 <= input_amount * (10000 - volume_fee_bps)`
   - This ensures proper fee deduction from the input amount and supports two outputs.

As a result:

- Once an on-chain verifier checks that the public `block_hash` corresponds to a real block in the underlying chain, all of the internal header fields (`parent_hash`, `block_number`, `state_root`, `extrinsics_root`, `digest`) are cryptographically bound to that real header via Poseidon2.
- Because the same `state_root` is also used in the storage proof, this ties the storage proof, the header, and the public block commitment together.

### Performance

In the case that proofs are aggregated, the dominant variable on-chain bandwidth cost becomes the aggregated public inputs:

- Per leaf proof, the aggregated proof carries:
  - `nullifier`: 4 felts
  - 2 output slots: 2 × (output_sum(1) + exit_account(4)) = 10 felts
  - Total: **14 felts per transfer** ≈ **112 bytes** (at 8 bytes/felt)

If we have 5MB blocks and plonky2 aggregated proofs are ~300KB, then a rough upper bound from *public-input bandwidth alone* is:

- `~4.9MB / 112B ≈ 43,750` transfers per block (ignoring small fixed overheads)

Compared to a typical 5MB / ~7.3KB ≈ 685 dilithium transactions, this is roughly a **60x+ throughput increase** under these assumptions.

At layer-0, each leaf contributes:
- 2 exit slots: 2 × (sum(1) + exit(4)) = 10 felts
- 1 nullifier: 4 felts
Total: 14 felts per leaf (≈112 bytes at 8 bytes/felt), plus a small fixed header.

Layer-1 adds a small fixed overhead (e.g., `aggregator_address`) and forwards the layer-0 slot/nullifier lists. Because layer-0 deduplicates exits only within each batch (and layer-1 forwards batches), further deduplication across batches—if desired—can be performed by the chain after verification.


### Security Notes

- Faulty proof verification or circuit implementation could create an inflation bug
- Users could prove an address is entangled by publishing the first hash `H(salt || secret)`
- Verification transactions will be [unsigned](https://github.com/polkadot-developers/knowledgebase/blob/master/current/learn-substrate/extrinsics.md)
- The storage proofs use a [felt-aligned zk-trie](./qip-0007.md) for efficient circuit verification
- The chain enforces a minimum total output amount for proofs to prevent dust attacks and ensure economic viability of verification
- Dummy proof handling is explicit and constrained by sentinel values; validation bypass occurs **only** when all dummy conditions are met.

### Balance-Linking Attack

A balance-linking attack occurs when an adversary attempts to correlate input and output transactions by analyzing the amounts involved. If an attacker can match the exact amount sent to an entangled address with the amount withdrawn, they can de-anonymize the transaction and link the sender to the recipient.

**Mitigations:**

1. **Quantization**: The output amounts are quantized with 0.01 units of precision, reducing the number of significant bits exposed.

2. **User-Controlled Output Reduction + Two-Output Splitting**: The circuit supports two output slots per proof. Users specify output amounts lower than their maximum entitlement (input minus fees) and can send the remainder to a second "change" address (or the same address) in the same proof. This avoids stranding funds, as a separate later withdrawal using the same secret/transfer_count would produce an identical nullifier and be rejected.

3. **Two-output splitting**: A single proof can split funds across two exit accounts (or create "change"), reducing direct amount correlation.

4. **Aggregation + deduplication**: Outputs can be aggregated; when duplicates occur, amounts are summed into a canonical slot and duplicate slots are zeroed, reducing linkability and making duplicate-vs-dummy indistinguishable.

5. **Dummy hiding**: Proof shuffling and dummy padding remove direct visibility into which leaf positions were real vs padding.

### Economic Notes

- The total supply of coins must be calculated via validator rewards, as entangled address spends appear to create new coins.
- We do this in Substrate by using the functions [`increase_balance` and `withdraw`](https://github.com/Quantus-Network/chain/blob/main/pallets/wormhole/src/lib.rs) to re-mint the coins and deduct fees.
- An inflation bug due to a faulty implementation would be economically-detectable only if the amount of reminted coins exceeded the sum of the balances of addresses that have 0 sends from them.

## Rationale

We use plonky2 as the proving system because:

- it uses FRI (from STARKs), which is post-quantum
- no trusted setup
- very efficient proving and verification
- Supports proof aggregation (plonky3 doesn't)
- rust-native
- reasonably easy to [get verifier](https://github.com/Quantus-Network/plonky2) into no-std state for Substrate

The nullifier construction uses `H(H(salt || secret || transfer_count))`, which prevents double-spending while allowing address reuse across different transactions. The salt "~nullif~" is used to domain-separate nullifier hashes.

The use of double hashing (`H(H(salt || secret))`) for unspendable accounts allows users to prove an address is entangled without revealing the secret. The salt "wormhole" is used for this derivation. In particular, dilithium public keys are much larger than 32 bytes, so a 32 byte preimage of an address could not be a dilithium pubkey.

The fee mechanism (volume_fee_bps) allows the protocol to collect fees on wormhole transactions while maintaining privacy of the exact input amount. Only the output amounts (after fee deduction) are revealed publicly.

The asset_id field enables support for multiple token types beyond the native token, allowing the wormhole system to handle various assets.
