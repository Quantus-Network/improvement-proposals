## Abstract

This document describes an aggregated post-quantum signature scheme for blockchains using zero-knowledge proofs. It moves balance-verification off-chain so that on-chain verification simply has to verify a single proof and update balances. It uses provably-unspendable addresses and nullifiers to prevent double-spends, and a dedicated [ZK-tree](./qip-0007.md) Merkle proof to prove that funding took place. These signatures can be aggregated because the proof system we use ["plonky2"](qip-0005/QIP-0005-2.pdf) supports aggregation via recursion. Aggregation is implemented as a multi-layer tree, with a privacy-sensitive layer-0 (`PrivateBatch`) and a layer-1 (`PublicBatch`) intended for third-party aggregators.
The limiting factor becomes the aggregated public inputs. In the current scheme, each leaf transfer contributes (in the final aggregated proof) one nullifier plus up to **two** output slots (exit accounts + amounts), while higher layers forward these slots and nullifiers and add a small fixed overhead.   
We call this scheme "wormhole addresses" because the unspendable addresses and exit addresses are invisibly linked, like wormhole qubits.

## Motivation

Transitioning to a post-quantum era in blockchains introduces a scaling challenge because post-quantum signatures and public keys are many times larger than those of elliptic curves and these typically need to be revealed to make a transaction. Secure hash algorithms (Poseidon in our case) are generally weakened but not destroyed by quantum algorithms (specifically Grover's). In fact, some post-quantum signature schemes such as SPHINCS+ are built on top of the security of secure hash functions, so proving knowledge of a preimage can suffice as a post-quantum signature scheme.

### ZK Circuit Details

**Public Inputs:**

- `asset_id`: The identifier for the asset being transferred (0 for native token).
- `output_amount_1`: Primary output amount, exposed as a `u32` quantized with 0.01 units of precision. On-chain, the amount is stored as a `u128` with 12 decimal places; during on-chain verification, we reconstruct this `u128` by multiplying `output_amount_1` by 10^10 (so that 10^2 × 10^10 = 10^12 total decimal precision).
- `output_amount_2`: Optional secondary output amount (change or split payment), also a `u32` quantized with 0.01 precision. Set to 0 if unused.
- `volume_fee_bps`: Volume fee rate in basis points (1 basis point = 0.01%). This is verified on-chain to match the runtime configuration.
- `nullifier`: A unique, transaction-specific value derived from private information. Its purpose is to prevent double-spending by ensuring that a given set of private inputs can only be used to generate one valid proof.
- `exit_account_1`: The public address where `output_amount_1` is intended to be sent after the proof is verified.
- `exit_account_2`: The public address where `output_amount_2` is intended to be sent (all zeros if unused).
- `block_hash`: A commitment (Poseidon2 hash) to the block header fields used inside the circuit.
- `block_number`: The block height corresponding to `block_hash`. This is public so the verifier/aggregator can check that it matches the associated header.

**Private Inputs:**

- `secret`: A confidential, randomly generated value unique to the prover, serves as a primary secret for deriving other transaction components.
- `transfer_count`: A per-recipient-account unique ID for the transfer (monotonically increasing), ensuring nullifiers are unique.
- `unspendable_account`: The wormhole (burn) address itself: `H(H("wormhole" || secret))`. This value is the `to` field of the ZK-tree leaf being spent (not a preimage of that address).
- `parent_hash`: The parent hash of the block header. **This is private** and is only used inside the circuit to compute `block_hash` from the header preimage (binding the header fields to the public commitment).
- `state_root`: The state root of the Substrate block. Still required as part of the header preimage (not used for deposit inclusion).
- `extrinsics_root`: The extrinsics root of the block header.
- `digest`: The raw header digest field (110 bytes), encoded injectively into a fixed number of field elements for use inside the circuit.
- `input_amount`: The deposit amount from the ZK-tree leaf (before fee deduction), quantized with 0.01 units of precision. The circuit verifies that:
  - `(output_amount_1 + output_amount_2) * 10000 <= input_amount * (10000 - volume_fee_bps)`.
- `zk_tree_root`: The ZK-tree root from the block header. Used both in the header preimage and as the expected root of the Merkle proof.
- `zk_merkle_siblings`: Sibling hashes for a 4-ary Poseidon Merkle proof of the deposit leaf (3 siblings per level, sorted).
- `zk_merkle_positions`: Position hints (0–3) for each level indicating where the current hash sits among the sorted siblings.


> Note: Instead of passing a monolithic `block_header` preimage into the circuit, we pass the structured header fields (`parent_hash`, `block_number`, `state_root`, `extrinsics_root`, `zk_tree_root`, `digest`) and recompute a Poseidon2 hash from them inside the circuit. That hash is constrained to equal the public `block_hash`. Deposit inclusion is proven against `zk_tree_root`, not against Substrate's MPT `state_root`.

### Miner Address Enforcement

The chain enforces that all miners use wormhole addresses for their block rewards. When a miner submits a block, they must provide a 32-byte preimage of their reward address. The chain hashes this preimage and sends rewards to the resulting address. Since dilithium public keys are much larger than 32 bytes, a valid 32-byte preimage cannot be a public key, ensuring the reward address is an wormhole (unspendable) address. This mechanism guarantees that all mining rewards flow through the wormhole system, maintaining the integrity of the wormhole address scheme across the network.

### Client / Prover Flow

User generates what appears to be a normal account but is provably unspendable "Proof-of-Burn". The account is unspendable because, instead of being a single-hash of a public key like a normal account, it is the double-hash of a salt + secret. The salt + double hashing protects the system from false-positives, where the zk-proof is convinced that the account is unspendable but actually the digest is a single-hash of a public key and therefore spendable. The security of the construction therefore reduces to finding the preimage of a preimage of a digest.

Users retain this proof of unspendability (secret pre-image) for later claims. Any tokens that are sent to the address are therefore provably burned, and so they can be re-minted without changing the total token supply.

The on-chain [ZK-tree](./qip-0007.md) records a leaf for **essentially every** native balance credit (ordinary transfers, mining rewards, vesting payouts, genesis, …), not only credits to wormhole addresses — with documented governance/hook-path exceptions (see QIP-0007; vesting pot→beneficiary payouts *are* recorded by the vesting pallet). Leaf data is `(to_account, transfer_count, asset_id, amount)`. For a wormhole spend, `to_account` is the unspendable address and `transfer_count` is that recipient's per-account counter. The tree root (`zk_tree_root`) is published in the block header. Because recorded credits grow the tree, circuit depth limits are a chain-wide liveness concern for wormhole proving (see QIP-0007).

The user's wallet opens a 4-ary Poseidon Merkle proof from a recent `zk_tree_root` down to the credit leaf. That Merkle path (`zk_merkle_siblings` + `zk_merkle_positions`), together with the leaf fields and header fields, becomes the private witness for the spend circuit. The per-recipient `transfer_count` is also included in the nullifier preimage along with a salt and the user's secret.

The secret used to create both the nullifier and the unspendable-account must be retained by the wallet and should therefore be derived deterministically from the wallet seed, similar to private/public keys (see [QIP-0002](./qip-0002.md) wormhole derivation path).

Unlike Substrate's MPT `state_root`, `zk_tree_root` is also available from on-chain pallet storage — but the runtime verifier still needs a **header-bound** commitment so that a proof cannot open against an arbitrary past or fabricated root. We therefore include the `block_hash` and `block_number` of the block header that contains `zk_tree_root` as public inputs. The circuit binds `zk_tree_root` to that public commitment by recomputing `block_hash` from structured header fields, and separately constrains the Merkle proof's computed root to equal that same `zk_tree_root`.

### Aggregator Flow

Anyone can aggregate proofs and submit the resulting aggregated-proof to the chain. However, aggregation is structured as a multi-layer tree, and the **privacy properties differ by layer**, so we recommend different operational roles at each layer.

#### Recommendation: Layer-0 (`PrivateBatch`) should be client-local

Although layer-0 aggregation is permissionless, **we recommend that layer-0 is used exclusively to aggregate a client’s own set of wormhole proofs** (i.e., performed locally by the wallet/client). In code this is `PrivateBatchProver` / the private-batch aggregator circuit.

Layer-0 is the layer where leaf proofs are padded with dummy proofs and where proof ordering / slot behavior is used to hide which transfers are real. If a client delegates layer-0 aggregation to a third party, that third party will typically learn (or be able to infer) **which leaf slots are real vs dummy** for that client’s batch (e.g., from the raw set of proofs provided, the count of real proofs, or the aggregation inputs prior to shuffling/padding). Revealing dummy locations materially weakens privacy because it makes **balance-linking analysis** much easier for the aggregator: the aggregator can narrow which output slots correspond to real transfers and correlate amounts/exit slots across time.

For this reason, layer-0 is treated as a **privacy-sensitive step** and should be executed by the client/wallet whenever possible.

#### Recommendation: Layer-1 (`PublicBatch`) is intended for delegated aggregation

Layer-1 aggregation, by contrast, operates over **already-aggregated layer-0 proofs** and simply verifies invariants and forwards the fixed-layout public inputs. In code this is `PublicBatchAggregator` / `PublicBatchProver`. At this stage, the delegated aggregator does not receive (and does not need) per-leaf “raw” proof sets or padding decisions; it aggregates **opaque layer-0 aggregates** whose internal dummy positions are already hidden inside a verified proof.

As a result, layer-1 does **not introduce the same privacy risks** as delegating layer-0, and is therefore the intended layer for **third-party / delegated aggregation** (e.g., run by miners, professional aggregators, or other infrastructure operators) to reduce on-chain submission overhead and collect aggregation fees.

#### Layer-0: aggregate leaf transfer proofs (client-local)

Layer-0 takes `N` leaf proofs (wormhole transfer proofs) and produces a single layer-0 aggregated proof. This step is privacy-sensitive due to dummy padding and should generally be performed by the client.

#### Layer-1: aggregate layer-0 aggregated proofs (delegated)

Layer-1 is intended for third-party aggregators who collect multiple layer-0 batches (from many clients) and combine them into a single proof for on-chain submission. Because it aggregates verified layer-0 proofs as opaque objects, it does not expose client dummy placement and is suitable for delegated operation.

#### Aggregated public input layouts

**Layer-0 aggregated proof output layout**

Layer-0 outputs a fixed-layout public input vector:

```text
[
  num_exit_slots(1),              // fixed = 2*N (two outputs per leaf)
  asset_id(1),
  volume_fee_bps(1),
  block_hash(4),
  block_number(1),
  [sum(1), exit_account(4)] * (2*N),
  nullifier(4) * N,
  padding...                      // padded so total len = 21*N + 8
]
```

> Note: Semantic payload is 8 + 14N felts (header + 2×5-felt exit slots + 4-felt nullifier per leaf). The circuit pads to `pi_len = LEAF_PI_LEN * N + 8` with `LEAF_PI_LEN = 21`. Exit slots are always 2*N (Bitcoin-style 2-output layout). Slots that are duplicates (within the batch) are zeroed (sum = 0 and exit_account = 0). Dummy leaves are detected via `block_hash == 0` (with zero outputs). Dummy leaf nullifiers are overridden with random dummy nullifiers in the wrapper output to prevent on-chain collisions.

**Layer-1 aggregated proof output layout**

Layer-1 aggregates M layer-0 proofs (each itself representing N leaves) and outputs an exact-length vector of `12 + 14*M*N` felts (no trailing padding):

```text
[
  aggregator_address(4),          // identifies the layer-1 operator for fee collection
  asset_id(1),
  volume_fee_bps(1),
  block_hash(4),
  block_number(1),
  total_exit_slots(1),            // = M * (2*N)
  [sum(1), exit_account(4)] * total_exit_slots,
  nullifier(4) * total_nullifiers // = M * N
]
```
> Note: Layer-1 forwards exit slots and nullifiers from each child layer-0 proof in order. Dummies at the layer-0 level propagate as block_hash == 0 in the layer-0 header and are permitted by layer-1’s “matches ref OR dummy” block constraint.

The deduplication and summing reduce the storage requirements for the chain. This aggregation process can be recursed, so that the many proofs being aggregated become leaves in a tree.

It's important to note that **all leaf proofs in an aggregated batch must use the same proof-generation block**. The aggregation circuit enforces that all real proofs (those with `block_hash != 0`) reference identical `block_hash` values. However, cross-block batching is still possible because ZK-tree leaves persist indefinitely: a deposit recorded in block X remains openable against the tree root at block Y (for any Y > X). To batch deposits from multiple blocks, a prover can generate Merkle proofs for all desired leaves against a single later block's `zk_tree_root`, and aggregate those proofs with a shared `block_hash`.

### Chain / Verifier Flow

The chain / verifier receives a proof that may be:
- a layer-0 aggregated proof, or
- a layer-1 (or higher) aggregated proof intended for on-chain submission.

The chain must check:

- The `block_hash` and `block_number` correspond to a valid block in the chain (per runtime constraints / depth window).
- The `volume_fee_bps` matches the current runtime configuration.
- The supplied proof is valid for the expected verifier circuit (layer-0 / layer-1).
- Each included `nullifier` has never been used before.
- For each non-zero exit slot (`exit_account != 0`), mint/transfer the corresponding `sum` to that account (after reconstructing `u128` from quantization), and apply fees per runtime rules.
- If present (layer-1+), `aggregator_address` is used to attribute and/or distribute aggregator fees (policy defined by the runtime).

### Circuit Logic

The zk-circuit verifies the following:

1. **Dummy Proof Detection**
   - If `block_hash == 0` and both `output_amount_1 == 0` and `output_amount_2 == 0`, the circuit derives `is_not_dummy = 0` and **conditionally** skips the nullifier hash binding and the block-hash / Merkle-root bindings.
   - Unspendable-account derivation, the ZK Merkle / fee fragment, exit-account wiring, and the `block_number` 32-bit range check still run unconditionally. In-repo dummy proofs therefore carry a real secret, non-zero `input_amount` / `volume_fee_bps`, and structurally valid witness data even though public outputs are zero — an all-zero witness will not satisfy the circuit.

2. **Nullifier Derivation**
   - Computes `H(H(salt || secret || transfer_count))` where salt is the 8-byte string "~nullif~"
   - Compares the derived value against the provided `nullifier` public input

3. **Unspendable Account Derivation**
   - Computes `H(H(salt || secret))` where salt is the 8-byte string "wormhole"
   - Compares the derived value with the provided `unspendable_account`

4. **ZK-Tree Merkle Proof Verification**
   - The circuit hashes the leaf `(unspendable_account / to, transfer_count, asset_id, input_amount)` with Poseidon2 and verifies a 4-ary Merkle path up to `zk_tree_root`
   - At each level (padded to circuit `MAX_DEPTH = 16`):
     1. Inserts the current hash among the 3 sorted siblings at the hinted position (0–3)
     2. Poseidon2-hashes the four children to produce the parent
   - The circuit constrains the Merkle proof's computed root to equal the private `zk_tree_root` input

5. **Block Header Commitment Verification**
   - Inputs: `block_number` (public), `parent_hash` (private), `state_root` (private), `extrinsics_root` (private), `zk_tree_root` (private), `digest` (private, 110 bytes mapped injectively to field elements)
   - Steps:
     1. **Range-check `block_number`**: The circuit constrains `block_number` to be a 32-bit value to ensure it matches the canonical encoding used outside the circuit
     2. **Build header preimage**: `preimage = parent_hash || block_number || state_root || extrinsics_root || zk_tree_root || digest`
     3. **Poseidon2 hash**: `computed_hash = Poseidon2Hash(preimage)` using `hash_n_to_hash_no_pad_p2::<Poseidon2Hash>`
     4. **Connect to public `block_hash`**: The circuit enforces `block_hash == computed_hash`
     5. **Bind Merkle root**: The circuit also enforces that header `zk_tree_root` equals the Merkle proof root

6. **Fee Calculation Verification**
   - The circuit verifies:
     - `(output_amount_1 + output_amount_2) * 10000 <= input_amount * (10000 - volume_fee_bps)`
   - This ensures proper fee deduction from the input amount and supports two outputs.

As a result:

- Once an on-chain verifier checks that the public `block_hash` corresponds to a real block in the underlying chain, all of the internal header fields (`parent_hash`, `block_number`, `state_root`, `extrinsics_root`, `zk_tree_root`, `digest`) are cryptographically bound to that real header via Poseidon2.
- Because the same `zk_tree_root` is also used in the Merkle proof, this ties deposit inclusion, the header, and the public block commitment together.

### Performance

In the case that proofs are aggregated, the dominant variable on-chain bandwidth cost becomes the aggregated public inputs:

- Per leaf proof, the aggregated proof carries:
  - `nullifier`: 4 felts
  - 2 output slots: 2 × (output_sum(1) + exit_account(4)) = 10 felts
  - Total: **14 felts per transfer** ≈ **112 bytes** (at 8 bytes/felt)

If we have 5MB blocks and plonky2 aggregated proofs are ~300KB, then a rough upper bound from *public-input bandwidth alone* is:

- `~4.9MB / 112B ≈ 43,750` transfers per block (ignoring small fixed overheads)

Compared to a typical 5MB / ~7.3KB ≈ 685 dilithium transactions, this is roughly a **60x+ throughput increase** under these assumptions.

At layer-0, the **semantic** per-leaf payload forwarded into aggregation is 14 felts (10 exit-slot + 4 nullifier), but the private-batch public-input vector is padded to **21 felts per leaf + 8-felt header** (`LEAF_PI_LEN * N + 8`).

Layer-1's on-chain bandwidth is the tighter figure above: exactly 14 felts of exit/nullifier payload per leaf across the batch, plus a 12-felt header (including `aggregator_address`). Because layer-0 deduplicates exits only within each batch (and layer-1 forwards batches), further deduplication across batches—if desired—can be performed by the chain after verification.


### Security Notes

- Faulty proof verification or circuit implementation could create an inflation bug
- Users could prove an address is wormhole by publishing the first hash `H(salt || secret)`
- Verification transactions will be [unsigned](https://github.com/polkadot-developers/knowledgebase/blob/master/current/learn-substrate/extrinsics.md)
- Deposit inclusion uses a [4-ary Poseidon ZK-tree](./qip-0007.md) for efficient circuit verification
- There is **no** minimum total-output / dust-amount check on verification: zero exit slots are skipped, and credits that fail existential-deposit minting are dropped after nullifiers are marked spent. Dust bundles can therefore succeed while silently producing no balance credit
- Circuit depth `MAX_DEPTH = 16` caps openable ZK-tree proofs; see QIP-0007 for capacity / growth implications (the tree records essentially all credits, with documented gaps, so growth is not limited to wormhole usage)
- Dummy proof handling uses sentinel public inputs; only the nullifier and block-hash/root bindings are gated on `is_not_dummy` (see Circuit Logic)

### Balance-Linking Attack

A balance-linking attack occurs when an adversary attempts to correlate input and output transactions by analyzing the amounts involved. If an attacker can match the exact amount sent to an wormhole address with the amount withdrawn, they can de-anonymize the transaction and link the sender to the recipient.

**Mitigations:**

1. **Quantization**: The output amounts are quantized with 0.01 units of precision, reducing the number of significant bits exposed.

2. **User-Controlled Output Reduction + Two-Output Splitting**: The circuit supports two output slots per proof. Users specify output amounts lower than their maximum entitlement (input minus fees) and can send the remainder to a second "change" address (or the same address) in the same proof. This avoids stranding funds, as a separate later withdrawal using the same secret/transfer_count would produce an identical nullifier and be rejected.

3. **Two-output splitting**: A single proof can split funds across two exit accounts (or create "change"), reducing direct amount correlation.

4. **Aggregation + deduplication**: Outputs can be aggregated; when duplicates occur, amounts are summed into a canonical slot and duplicate slots are zeroed, reducing linkability and making duplicate-vs-dummy indistinguishable.

5. **Dummy hiding**: Proof shuffling and dummy padding remove direct visibility into which leaf positions were real vs padding.

### Economic Notes

- The total supply of coins must be calculated via validator rewards, as wormhole address spends appear to create new coins.
- We do this in Substrate by using the functions [`increase_balance` and `withdraw`](https://github.com/Quantus-Network/chain/blob/main/pallets/wormhole/src/lib.rs) to re-mint the coins and deduct fees.
- An inflation bug due to a faulty implementation would be economically-detectable only if the amount of reminted coins exceeded the sum of the balances of addresses that have 0 sends from them.

## Rationale

We use plonky2 as the proving system because:

- it uses FRI (from STARKs), which is post-quantum
- no trusted setup
- very efficient proving and verification
- Supports proof aggregation (plonky3 doesn't)
- rust-native
- reasonably easy to [get verifier](https://github.com/Quantus-Network/qp-plonky2) into no-std state for Substrate

The nullifier construction uses `H(H(salt || secret || transfer_count))`, which prevents double-spending while allowing address reuse across different transactions. The salt "~nullif~" is used to domain-separate nullifier hashes.

The use of double hashing (`H(H(salt || secret))`) for unspendable accounts allows users to prove an address is wormhole without revealing the secret. The salt "wormhole" is used for this derivation. In particular, dilithium public keys are much larger than 32 bytes, so a 32 byte preimage of an address could not be a dilithium pubkey.

The fee mechanism (volume_fee_bps) allows the protocol to collect fees on wormhole transactions while maintaining privacy of the exact input amount. Only the output amounts (after fee deduction) are revealed publicly.

The asset_id field enables support for multiple token types beyond the native token, allowing the wormhole system to handle various assets.
